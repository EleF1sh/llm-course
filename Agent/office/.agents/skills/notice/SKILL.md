# 通知写作助手 V1.1｜DOCX 版

## 概述

本 Skill 提供"生成初稿 → 事实复核 → 自动修订 → 保存 Markdown 最终稿 → DOCX 自动套版"的完整工作流。只处理"通知"文种。

**版本状态：** 1.1.0 (Pre-release)。Phase 1 架构收敛：内容解析层（notice_model.py）已独立，Renderer（fill_tongzhi_docx.py）已纯化。排版底层（notice_document_factory.py）冻结。

## 触发范围

当用户提出以下任务时调用本 Skill：
- 写一份通知
- 起草通知
- 根据材料整理通知
- 修改通知
- 生成通知文稿

本 Skill 只处理"通知"文种，不处理请示、报告、函、纪要等其他文种。

## 用户输入

Skill 应从用户输入中识别并整理以下内容：
1. 主要任务
2. 原始材料
3. 特殊要求
4. 可选：主送对象、发文单位、成文日期、输出文件名

如果用户没有单独填写字段，应从自然语言输入中识别。

## 材料不足时的处理

通知必须存在明确的"通知事项"。如果以下核心内容尚未确定：
- 通知对象（发给谁）
- 通知什么事
- 核心事项是否明确（如会议时间地点、工作要求、活动安排等）

不得自行替用户作出决定，也不得使用占位符拼成一份表面完整的通知。应先向用户提出最少量的必要问题。

此时：
1. 不生成 draft_v1；
2. 不生成 Markdown 最终稿；
3. 不生成 DOCX；
4. 不自行选择通知事项；
5. 只提出完成任务所必需的最少问题。

但发文日期、主送对象等一般格式信息未确定时，统一使用以下占位符，不得自行推定具体内容：
- `〔主送机关〕`（后跟冒号，冒号只出现一次）
- `〔日期〕`

## 标准工作流程

必须按以下顺序执行：

### 步骤 0：保存原始材料并建立动态事实清单（notice_facts.json）

**每次任务开始时，必须先原样保存用户原始材料，再根据用户本次提供的材料创建独立事实清单。**

工作流顺序：

1. **原样保存用户原始材料**：将用户提供的原始材料原样保存为文件（如 `用户原始材料.txt`），保存到当前任务输出目录。原始材料文件不得从最终 Markdown 反向生成。

2. **创建 notice_facts_draft.json**：根据原始材料整理动态事实字段，保存为 `notice_facts_draft.json`（草稿，不含 source_sha256）。

3. **调用 create_notice_facts.py 生成正式 notice_facts.json**：
```bash
python3 scripts/create_notice_facts.py \
  --source "/abs/path/用户原始材料.txt" \
  --draft "/abs/path/notice_facts_draft.json" \
  --output "/abs/path/notice_facts.json"
```

`source_sha256` 必须由 `create_notice_facts.py` 脚本通过读取原始材料文件原始字节计算得出，**不允许 LLM 手工填写或猜测 source_sha256**。

事实清单结构如下：

```json
{
  "schema_version": "1.0",
  "source_sha256": "<由create_notice_facts.py计算的64位SHA-256>",
  "required_exact": [{"field": "字段名", "value": "必须出现在成稿中的精确文本"}],
  "required_items": [{"field": "字段名", "items": ["逐项检查的列表"]}],
  "forbidden_exact": [{"field": "字段名", "value": "不得出现在成稿中的文本"}],
  "contact": {"name": "联系人姓名", "phone": "联系电话", "email": "电子邮箱"},
  "issuer": "发文单位完整名称",
  "document_date": "成文日期"
}
```

**关键规则：**
- `notice_facts.json` 必须在最终 Markdown 之前生成。
- 所有值必须来自当前用户材料，不得使用测试样本中的时间、地点、人员或联系方式作为默认值。
- 不得将历史任务事实复用于新任务。原始材料变化后必须重新生成 `notice_facts.json`。
- 禁止在脚本中硬编码业务事实。所有固定测试断言只能放在 `tests/` 目录中。
- 材料不足时停止并向用户补充询问，不得用无关值填充事实清单。
- `source_sha256` 必须是字符串、64位、只包含 0-9 和 a-f，对应 source 文件原始字节的 SHA-256。

### 步骤 1：生成初稿（draft_v1）

使用通知写作核心规则，对照用户任务和原始材料生成第一版通知。

通知写作核心规则通过加载 `prompts/通知生成提示词.md` 获得，关键要求：

**严格材料模式：**
- 只可排序、去重、分类、正式化口语、添加不改变含义的连接语、按材料增删章节和使用占位符。
- 每句实质性陈述必须有直接依据。不得因"通知应具体"而补写通知对象、任务、责任单位、时间节点、报送要求、检查方式、纪律要求、监督机制、政策依据或工作成效。
- 先据材料判断印发/转发、部署、事务知照等用途。印发、转发的文件标题、机关和文号须来自材料。
- 通知对象、事项、责任主体、时限和办理要求必须来自材料。材料只提供事项时，不自动生成"各单位要高度重视、按时报送、加强督查"。
- 区分已发布、现予发布、自某日起执行、拟执行；不得把计划变为已决定。
- 数据冲突不任选、不合并、不擅算。成文日期不由执行日期或报送截止日期推定。
- 常用结构：标题、主送对象、缘由/依据（有材料才写）、通知事项、材料已有的执行要求、落款日期、附件说明（如有）。知照性通知可直叙。
- **发文单位全称规则：** 当原始材料提供了发文单位的明确全称时（如"公司综合管理部"），必须使用材料中的完整名称，不得自行简称。

内部结果命名为 draft_v1。第一版初稿不直接展示给用户。

### 步骤 2：独立事实复核（review_result）

加载 `prompts/统一事实一致性复核模板_V1.1.md` 中的复核规则。

**重要说明：** 在当前 WorkBuddy Skill 机制下，Skill 的所有内容在同一个对话上下文中运行，无法实现真正的独立子任务、独立上下文或独立模型调用。本步骤通过在同一对话中严格切换角色来完成复核——即先完成初稿写作，再以复核员身份独立审查，不将写作时的推理带入复核过程。

复核员身份切换后，对以下四项内容进行复核：
1. 用户主要任务
2. 用户特殊要求
3. 原始材料
4. draft_v1

复核必须严格遵守 `prompts/统一事实一致性复核模板_V1.1.md` 中的所有规则。

内部结果命名为 review_result。

### 步骤 3：自动修订（final_draft）

根据原始材料、用户任务、draft_v1 和 review_result 生成最终稿。

**修订最高原则：**
- 原始材料和用户任务是最高依据
- 复核意见只是参考，不得机械执行
- 只做最小必要修改，不得重新自由创作全文
- 不得在修订过程中产生新的事实、数据、日期、原因、措施或结论

**允许自动修改的情况：**
- 删除原始材料没有提供的事实
- 删除无依据的评价、原因、措施和效果
- 补回原始材料中明确提供但初稿遗漏的信息
- 恢复被改变的时间、进度和完成状态
- 恢复正确的发文主体、责任部门和主送对象
- 恢复"建议、讨论、认为、决定、要求"等准确权威层级
- 删除 Markdown 符号、代码框、横线和说明性文字
- 修正明显错别字、标点和不改变原意的病句
- 将未经确认的具体日期、单位等恢复为占位符

**不得自动决定的内容：**
- 主送对象具体名称
- 尚未确定的通知事项
- 通知对象范围
- 任务分工和责任单位
- 执行期限和截止日期
- 新增工作要求
- 新增监督或检查机制
- 新增报送要求
- 是否形成监督检查后果
- 是否扩大通知范围

内部结果命名为 final_draft。

### 步骤 4：复核误报处理

出现以下情况时，不采纳相应复核意见：
1. 复核内容引用了其他文种或其他任务
2. 复核要求补写原始材料没有的信息
3. 复核把正常通知结语误判为材料外新增
4. 复核要求把 AI 建议写成单位已经确定的措施
5. 复核意见会改变事实、日期、主体、通知事项或状态
6. 复核中出现与当前通知无关的请示、纪要、讲话稿等上下文串扰

### 步骤 5：最终静默检查

生成 final_draft 后，再检查以下 9 项：
1. 通知事项是否明确
2. 调整前后的日期、数量、名称是否准确
3. 是否增加材料外原因
4. 是否改变当前进展状态
5. 是否增加执行要求、监督或报送内容
6. 是否错置发文主体和主送对象
7. 是否擅自生成成文日期
8. 是否残留 Markdown 格式
9. 是否出现内部矛盾

发现问题时，在输出前完成修正。

### 步骤 6：标题与落款规则

**标题规则：**
1. 短标题单行
2. 长标题可两行
3. 必须按完整词组断行
4. 不得拆开"关于开展""关于印发""数字化""所属单位""完成期限"等完整词语
5. 标题只出现在第一页
6. 不得改变标题原文字

**落款规则：**
1. 使用材料中的完整发文单位
2. 不得自行简称
3. 发文单位位于日期上方
4. 发文单位与日期形成统一右侧落款区域
5. 主送对象未确定时使用 `〔主送机关〕：`
6. 日期未确定时使用 `〔日期〕`
7. 冒号不得重复
8. 通知无固定结语，正文最后一段即为结尾

### 步骤 7：保存 Markdown 最终稿

将完整最终稿保存为文件。默认文件名：`通知_最终稿.md`，保存到当前工作目录。

### 步骤 8：Markdown 解析 → NoticeModel → DOCX 生成（Phase 1 架构收敛）

**架构变化（V1.1 Phase 1）：** 内容解析与 DOCX 渲染已分离。

- `scripts/notice_model.py`：唯一内容解析层，负责 Markdown → NoticeModel
- `scripts/fill_tongzhi_docx.py`：纯 Renderer，只负责 NoticeModel → DOCX

从 final_draft Markdown 生成 DOCX 的流程：

1. `notice_model.py` 解析 Markdown，生成 NoticeModel JSON
2. `fill_tongzhi_docx.py` 读取 NoticeModel JSON，渲染为 DOCX

NoticeModel 字段：
```json
{
  "title_text": "完整标题文本",
  "main_recipient": "主送对象（不含冒号）",
  "preamble": "导语过渡句（如'现就……通知如下：'）",
  "body_blocks": [
    ["paragraph", "正文第一段"],
    ["heading1", "一、一级标题"],
    ["paragraph", "一级标题对应的正文内容"],
    ["heading2", "（一）二级标题"],
    ["paragraph", "二级标题对应的正文内容"],
    ["contact", "联系人：张三"],
    ["contact", "联系电话：010-88889999"]
  ],
  "issuer": "发文单位完整名称",
  "document_date": "成文日期或〔日期〕"
}
```

**关键规则：**
- 标题必须为 `# 完整标题文本`，单行，禁止跨行拆写
- 导语由 notice_model.py 唯一决定：Markdown 中有唯一导语则保留，无则自动生成，>1个则报错
- 标题视觉换行由 fill_tongzhi_docx.py 负责（Renderer 职责）
- 发文单位必须使用材料中的完整名称，不得自行简称
- 通知无固定结语，正文最后一段即为结尾

统一交付命令：
```bash
python3 scripts/build_and_validate_notice.py \
  --source "/abs/path/用户原始材料.txt" \
  --facts "/abs/path/notice_facts.json" \
  --input "/abs/path/通知_最终稿.md" \
  --output "/abs/path/通知.docx"
```

管道内部自动完成 Markdown 解析 → NoticeModel → Renderer 流程。

必须使用 final_draft 生成 DOCX，不得使用 draft_v1。

### 步骤 9：自动检查

DOCX 生成完成后，重新读取并检查：
1. 标题是否正确
2. 主送对象是否正确
3. 正文段落是否完整
4. 发文单位是否完整
5. 日期占位符是否正确
6. 是否残留模板占位符
7. 是否残留 Markdown 符号
8. 每个段落是否应用正确的 Word 样式
9. 文本是否与 final_draft 一致
10. 是否残留请示文种专用词汇（如"妥否，请批示"、"以上请示"等）

Markdown 和 DOCX 必须使用同一个 final_draft，内容不得出现差异。

能够渲染 PDF 时，可增加视觉检查。不能渲染时，如实标记"已完成 DOCX 结构和样式检查，未完成独立 PDF 视觉渲染。"

## 最终交付物规则

当用户提供的信息已经完整并通过事实冲突检查后，本Skill必须生成真实的`.docx`文件。

最终交付物必须是带有通知公文格式的Word文档，不得仅输出聊天正文、Markdown、HTML或生成建议。

Markdown仅作为生成DOCX的内部中间格式，不得作为默认最终交付物。

必须实际调用统一交付脚本：

```bash
python3 scripts/build_and_validate_notice.py \
  --source "/abs/path/用户原始材料.txt" \
  --facts "/abs/path/notice_facts.json" \
  --input "/abs/path/通知_最终稿.md" \
  --output "/abs/path/通知.docx"
```

`--source`、`--facts`、`--input`、`--output` 全部必填。

管道顺序为：
1. 环境预检（preflight_check.py）
2. 检查 source 文件存在且非空
3. 检查 facts 文件存在
4. 重新计算 source 文件 SHA-256，与 facts 中的 source_sha256 比较
5. Markdown 事实复核（fact_check_notice.py --markdown-only，传入 --source）
6. Markdown 解析 → NoticeModel（notice_model.py，唯一内容解析层）
7. DOCX 生成（fill_tongzhi_docx.py，纯 Renderer，接收 NoticeModel JSON）
8. DOCX 事实复核（fact_check_notice.py 完整模式，传入 --source）
9. DOCX 结构校验（validate_notice_docx.py，含语义校验）
10. ARTIFACT_READY

source 哈希不一致时，必须在 DOCX 生成之前终止，不得创建 DOCX，不得输出 ARTIFACT_READY，返回非零退出码。

Markdown 事实复核和 DOCX 事实复核调用 fact_check_notice.py 时，必须都传入同一个 --source。

facts 文件不存在或事实复核失败时，禁止输出 ARTIFACT_READY。

不得仅说明"可以生成Word"而不执行脚本。

DOCX校验成功后，读取`ARTIFACT_READY`返回的完整路径，将该DOCX作为WorkBuddy任务产物交付用户。

**只有以下情况允许不生成DOCX：**
1. 用户信息不足；
2. 用户材料存在未解决的事实冲突；
3. Python运行环境或必要依赖不可用；
4. 输出目录没有写入权限；
5. DOCX生成或校验失败；
6. 用户明确要求只输出纯文本或Markdown。

发生运行错误时，必须明确报告错误，不得把Markdown伪装成已经完成的Word交付。

## 向用户展示的内容

对话界面**不展示**以下内容：
- 第一版初稿（draft_v1）
- 完整复核报告（review_result）
- 内部执行过程
- 内部推理
- 内部结构化 JSON
- 完整最终稿正文

**只向用户展示本次实际修改的内容和最终稿保存位置，并交付DOCX文件。**

```
通知已完成生成、复核、自动修订和 DOCX 套版。

本次共修改 X 处：
修改 1 位置：…… 修改前：…… 修改后：…… 原因：……

最终文件：
通知 DOCX：[文件路径]（已通过结构校验）
通知文本稿：[文件路径]
```

如果没有发现需要修改的内容：

```
通知已完成生成和复核。未发现需要修改的内容，已保留首次生成稿。

最终文件：
通知 DOCX：[文件路径]（已通过结构校验）
通知文本稿：[文件路径]
```

DOCX校验成功后，必须将该文件作为任务产物交付给用户，不得仅回复文件路径。

如果材料不足以形成通知：

```
当前材料不足以明确通知事项，需要补充以下信息：
1. ……
2. ……
```

## 禁止事项

1. 不得用未复核的初稿（draft_v1）生成 DOCX
2. 不得把复核报告或修改清单写入 DOCX
3. 不得自行增加红头、发文字号、版记、印章或密级
4. 不得声称已完全符合所有单位正式发文规范
5. 不得修改 qingshi-writer-v2.1-docx 的任何文件
6. 不得修改旧版 qingshi-writer
7. 不得覆盖通用母版或其他模板文件
8. 不得在通知中出现请示专用结语（如"妥否，请批示"）
